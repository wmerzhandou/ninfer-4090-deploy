# 参数与容量说明

本文解释生产启动参数的含义、默认值和调整边界。除非有明确的回归测试，不要改动
“固定值”一列。

## 1. 核心启动参数

| 参数 | 固定值 | 作用 | 调整建议 |
|---|---:|---|---|
| `--max-context` | `262144` | 单请求可见的总上下文上限（prompt + 生成 + KV） | 不建议降低；降低不会提升已有短请求速度 |
| `--kv-capacity` | `1048576` | 单实例 KV 池 token 容量 | 48 GB 卡保持 1,048,576；不要低于 `max-context` |
| `--max-concurrency` | `6` | 同时活跃的请求 lane 数 | 1..8；6 是吞吐/延迟折中，8 是硬上限 |
| `--max-pending-requests` | `16` | 等待队列上限 | 太小会在突发时直接拒绝；太大只会让排队更久 |
| `--pending-timeout-ms` | `600000` | 排队超时（10 分钟） | 长任务不要调小 |
| `--max-private-continuations` | `32` | 私有续接/会话缓存槽 | 多客户端长会话可保持 32 |
| `--max-shared-prefixes` | `12` | 共享前缀缓存槽 | 不要让所有会话都挤同一前缀 |
| `--host-state-slots` | `16` | host 侧状态槽 | 与并发和续接数量匹配 |
| `--host-kv-mib` | `16384` | host 侧 KV 预留（MiB） | 本机 16 GiB；host 内存不足时再降 |
| `--prefill-chunk` | `2048` | prefill 分块 | 必须 <= 2688；大于 2688 走 unsplit schedule，精度和稳定性都变差 |
| `--kv-dtype` | `rk4v4-e8` | KV 量化格式 | 换格式会改变容量、速度和数值；必须重新做回归 |
| `--default-max-tokens` | `65536` | 请求未写 `max_tokens` 时的默认输出上限 | 不是模型上下文；请求可以显式覆盖 |
| `--prefill-activations` | `a16` | prefill 激活精度/路径 | 已验证组合，不要随意改 |
| `--spec mtp` | 开启 | MTP3 投机解码 | 关闭后速度下降，但用于 baseline 回归 |
| `--draft-tokens` | `3` | MTP3 draft 数 | 不是越大越好；3 是本机验证值 |
| `--lm-head-draft` | 开启 | 用 LM head 生成 draft | 与 MTP3 配套 |
| `--prompt-lookup-tokens` | `15` | K15 prompt lookup 窗口 | `fast` 档启用；复制型编辑收益明显 |
| `--prompt-lookup-min-match` | `12` | 最小匹配长度 | 12 是已验证值；太低会误配 |
| `--vision` | 开启 | 图片/视频输入 | 关闭可省一点显存，但客户端会失去视觉能力 |
| `--vision-max-tokens` | `8192` | 视觉 scratchpad 上限 | 大图/多图可上调，但会增加显存和延迟 |
| `--no-cuda-graph` | 开启 | 关闭 CUDA Graph | 当前稳定组合；不要为了少量读数去掉 |
| `--device 0` | 固定 | 实例内部逻辑设备 | 物理卡由 `CUDA_VISIBLE_DEVICES` 选择 |

## 2. `max_tokens`、上下文和思考预算

这三个概念容易混淆：

1. `--max-context 262144`：模型这一次请求最多能“看见 + 生成”多少 token；
2. `--default-max-tokens 65536`：客户端没有传 `max_tokens` 时的默认输出上限；
3. 请求里的 `max_tokens` / `max_output_tokens`：这一次请求的实际输出预算，包含
   思考 token 和最终答案 token。

因此：

- 启动参数里没有单独的“思考预算”；思考长度由请求的 `reasoning_effort` 和
  `max_tokens` 共同约束；
- 使用 `xhigh` 或长推理链时，`max_tokens=16384` 可能只够思考、不够答案；应显式
  提高到 32768 或 65536，并确认总上下文没有超过 262144；
- 把 `--default-max-tokens` 设成 65536 不会让每个请求都生成 65536，只是默认上限；
- 客户端显式传较小的 `max_tokens` 时，以客户端为准。

## 3. 并发容量怎么估

粗略估算：

```text
活跃并发 × 单会话上下文 ≈ KV 压力
```

1,048,576 token 的 KV 池对 6 路、每路 100K–150K 的会话仍有空间；但 prefill 计算
和 host 内存带宽会先成为瓶颈。实际选择：

| 使用方式 | 建议并发 |
|---|---:|
| 一个人用 Codex/dsh，追求跟手 | 4 |
| 2–4 个同事同时用，要求吞吐 | 6 |
| 短请求突发、能接受 TTFT 变长 | 8 |
| 长上下文 + 多并发 + 视觉 | 4–6，必要时降视觉 token |

不要用“显存还剩很多”直接推高并发。`nvidia-smi` 的显存占用只是结果之一，调度、
prefill 和 host KV 带宽都会限制体感。

## 4. 缓存相关参数

- `--max-private-continuations 32`：每个会话的私有续接槽；长对话多时不要太小；
- `--max-shared-prefixes 12`：共享前缀槽；适合多个请求共享同一 system prompt；
- `--host-state-slots 16`：host 侧状态槽；与并发/续接配合；
- `--host-kv-mib 16384`：host KV 预留；主机内存紧张时再降，不要为了“看起来快”
  盲目拉满。

缓存是进程内的。跨端口不共享；重启即清空；system prompt、工具清单或图片前的
内容变化都会导致前缀失效。

## 5. 不建议修改的参数

以下组合已经过真实 Codex/dsh 任务和回归验证，除非你能重跑完整验收，否则不要动：

```text
--prefill-chunk 2048
--kv-dtype rk4v4-e8
--prefill-activations a16
--spec mtp --draft-tokens 3 --lm-head-draft
--prompt-lookup-tokens 15 --prompt-lookup-min-match 12
--vision-max-tokens 8192
--no-cuda-graph
```

特别是：

- 不要把 `--prefill-chunk` 改成大于 2688；
- 不要在 DFlash 后端上期待 JSON Schema；引擎会返回
  `unsupported_json_schema`；
- 不要把 `--max-concurrency` 设为大于 8；脚本会拒绝；
- 不要用 container v3 模型；
- 不要在同一个物理 GPU 上起两个实例。
