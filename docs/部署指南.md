# RTX 4090 48G · Qwen3.8-27B NInfer 部署指南

本文面向一台与本机近似硬件的新机器：单机多张 RTX 4090 48 GB，Linux，
每张卡跑一个独立 NInfer 实例。目标是直接复现已验证的生产配置，而不是重新做
一轮 kernel 实验。

## 0. 结论先行

本机生产形态：

| 实例 | 物理 GPU | 端口 | profile | 并发 | 上下文 | KV 池 |
|---|---:|---:|---|---:|---:|---:|
| `8003` | 1 | 8003 | `fast` | 6 | 262,144 | 1,048,576 |
| `8004` | 2 | 8004 | `fast` | 6 | 262,144 | 1,048,576 |
| `8005` | 0 | 8005 | `fast` | 6 | 262,144 | 1,048,576 |

三个实例使用同一份二进制、同一份模型、同一组参数；它们不共享缓存或会话，也
不做自动负载均衡。客户端指向哪个端口，就使用哪个实例。

`fast` = A16 + MTP3 + K15 prompt lookup；`pure` = A16 + MTP3，无 lookup；
`baseline` = 无投机解码、无 lookup，仅用于诊断。

## 1. 前置条件

### 1.1 已验证环境

- NVIDIA GeForce RTX 4090 48 GB × 4，单卡显存 `49,140 MiB`，功耗上限 `450 W`；
- 驱动 `590.48.01`；
- CUDA toolkit `12.8.61`；
- GCC/G++ `13.4.0`；
- CMake `4.4.5`（仓库要求 3.28+）；
- Ninja；
- FFmpeg 开发库（`libavformat`、`libavcodec`、`libavutil`、`libswscale`）；
- libcurl 7.85+ 开发库；
- 模型所在磁盘至少留出 20 GB 临时空间。

驱动、功耗上限、散热和 CUDA 版本会直接影响 tok/s。新机器的读数不能直接和本机
历史读数混排；先跑一次 `scripts/smoke-test.sh`，再记录本机基线。

### 1.2 Ubuntu 依赖示例

```bash
sudo apt-get update
sudo apt-get install --yes \
  build-essential gcc-13 g++-13 cmake ninja-build pkg-config \
  libavcodec-dev libavformat-dev libavutil-dev libswscale-dev \
  libcurl4-openssl-dev
```

确认工具链：

```bash
nvidia-smi
nvcc --version
gcc-13 --version | head -1
cmake --version | head -1
pkg-config --modversion libavformat libcurl
```

## 2. 取源码并应用生产补丁

补丁的基线是上游 `rtx4090-port` 的 `7f47a62282b8e9d3c3b03bd6750d0bfe37e9bb66`。
不要拿 `master`，也不要直接使用上游最新 HEAD；先后顺序是“固定基线 → 应用补丁”。

```bash
git clone https://github.com/sergiuszm/ninfer-4090.git
cd ninfer-4090
git switch -c 4090-stable 7f47a62282b8e9d3c3b03bd6750d0bfe37e9bb66
git apply --3way /path/to/ninfer-4090-deploy/patches/ninfer-4090-stable.patch
git status --short
```

补丁包含：

- prompt-lookup / K15 的 CLI、运行时缓冲和调度；
- Codex Responses 的 `reasoning.encrypted_content` 兼容；
- JSON `response_format`（`json_object` / `json_schema`）与 XGrammar token mask；
- 视觉输入路径；
- 多 lane / 投机解码的调度修正；
- KV 分页 entitlement 预留、worker 异常原地恢复、错误正文日志；
- 相关测试。

如果 `git apply --check` 失败，先确认 HEAD 是上面的基线 commit。不要用
`git apply --reject` 把冲突文件拼成半成品；冲突说明基线不对或上游已改动。

```text

container: v2
size:      18,210,531,328 bytes (16.96 GiB)
SHA-256:   eec39564993d6e9c7d5e383382a760f093465c9d163ec9a1bd6b80199514bf3e
```

```bash
NINFER_MODEL_DIR="$PWD/models" \
  /path/to/ninfer-4090-deploy/scripts/download-model.sh
```

如果 Hugging Face 直连失败，可以使用镜像，但**最终必须校验同一个 SHA-256**：

```bash
HF_ENDPOINT=https://hf-mirror.com \
NINFER_MODEL_DIR="$PWD/models" \

```

报：

```text
artifact magic is not NInfer v2
```

## 4. 构建

### 4.1 标准构建

```bash
export CC=/usr/bin/gcc-13
export CXX=/usr/bin/g++-13
export CUDACXX=/usr/local/cuda-12.8/bin/nvcc
export CUDAHOSTCXX="$CXX"

/path/to/ninfer-4090-deploy/scripts/build.sh
```

等价的手工命令：

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_C_COMPILER="$CC" \
  -DCMAKE_CXX_COMPILER="$CXX" \
  -DCMAKE_CUDA_COMPILER="$CUDACXX" \
  -DCMAKE_CUDA_HOST_COMPILER="$CUDAHOSTCXX" \
  -DCMAKE_CUDA_ARCHITECTURES=89 \
  -DNINFER_BUILD_APPS=ON \
  -DBUILD_TESTING=OFF \
  -DNINFER_BUILD_BENCHMARKS=OFF

cmake --build build --target ninfer-serve --parallel 4
```

产物：

```text
build/apps/ninfer-serve
```

### 4.2 已验证的 conda 工具链

如果想复现本机的编译器组合，可以使用 conda-forge 的 GCC 13 / CMake 4.x /
FFmpeg / libcurl：

```bash
export CC=/opt/conda/envs/build/bin/x86_64-conda-linux-gnu-gcc
export CXX=/opt/conda/envs/build/bin/x86_64-conda-linux-gnu-g++
export CUDACXX=/usr/local/cuda-12.8/bin/nvcc
export CUDAHOSTCXX="$CXX"
export PKG_CONFIG=/opt/conda/envs/build/bin/pkg-config
export PKG_CONFIG_PATH=/opt/conda/envs/build/lib/pkgconfig

/path/to/ninfer-4090-deploy/scripts/build.sh
```

如果 conda 的 `libcurl.pc` 报 `zlib` 找不到，安装 `zlib1g-dev`，或在
`PKG_CONFIG_PATH` 中提供对应版本的 `zlib.pc`。这是构建期依赖问题，不是引擎
运行时问题。

### 4.3 构建注意事项

- 必须 `CMAKE_CUDA_ARCHITECTURES=89`；其他架构会被 CMake 直接拒绝。
- CUDA 必须 >= 12.8。
- 不建议用不同 CUDA/GCC 组合的二进制直接混排读数。
- 生产二进制可以复制到其他同架构机器做快速验证，但长期部署仍建议从源码重建。

## 5. 启动实例

先设置三个公共变量：

```bash
export NINFER_SERVER="$PWD/build/apps/ninfer-serve"
export NINFER_MODEL="$PWD/models/qwen3_8_27b.ninfer"
export NINFER_API_KEY="replace-with-a-private-key"
```

启动：

```bash
/path/to/ninfer-4090-deploy/scripts/start-8003.sh
/path/to/ninfer-4090-deploy/scripts/start-8004.sh
/path/to/ninfer-4090-deploy/scripts/start-8005.sh
```

默认卡号是 `8003→GPU1`、`8004→GPU2`、`8005→GPU0`。机器编号不同就用
`NINFER_GPU` 覆盖，例如把 8005 换到 GPU3（确认该卡空闲）：

```bash
NINFER_GPU=3 /path/to/ninfer-4090-deploy/scripts/start-8005.sh
```

如果 8005 没有占用 GPU3，第四张卡需要额外实例时可以用通用启动器；它不会自动
加入 systemd：

```bash
/path/to/ninfer-4090-deploy/scripts/start-ninfer.sh --port 8006 --gpu 3
```

查看实际命令（不启动）：

```bash
/path/to/ninfer-4090-deploy/scripts/start-8003.sh --print-command
```

切换 profile 或重启：

```bash
NINFER_PROFILE=pure /path/to/ninfer-4090-deploy/scripts/start-8003.sh --restart
```

停止手工实例：

```bash
/path/to/ninfer-4090-deploy/scripts/stop-ninfer.sh --port 8003
```

启动脚本会：

1. 校验二进制、模型、端口、并发、prefill chunk；
2. 如果已有 PID 文件，校验它确实属于同一个端口，避免误杀；
3. 用 `setsid nohup` 拉起并写 PID；
4. 等待 `/health` 返回 `{"status":"ok"}`，默认最多 300 秒；
5. 失败时打印日志尾部并回收进程。

## 6. systemd 用户服务

直接编辑 `config/8003.env`、`config/8004.env`、`config/8005.env`，至少把
`NINFER_API_KEY` 从 `change-me` 改掉。

安装并启用：

```bash
/path/to/ninfer-4090-deploy/scripts/install-systemd.sh --enable --watchdog
```

如果希望退出登录后服务继续运行：

```bash
loginctl enable-linger "$USER"
```

常用命令：

```bash
systemctl --user status ninfer-8003.service
journalctl --user -u ninfer-8003.service -f
systemctl --user restart ninfer-8003.service
systemctl --user reset-failed ninfer-8003.service
```

systemd 使用 `--foreground`，不会创建第二套 PID 管理。不要同时用
`start-8003.sh` 和 systemd 启动同一个端口。

## 7. 局域网访问

默认 `--host 0.0.0.0`，因此同一局域网内可以访问：

```text
http://<SERVER_IP>:8003/v1
http://<SERVER_IP>:8004/v1
http://<SERVER_IP>:8005/v1
```

健康检查在 `/health`，不在 `/v1` 下：

```bash
curl http://<SERVER_IP>:8003/health
```

客户端请求头：

```text
Authorization: Bearer <NINFER_API_KEY>
```

`--api-key` 是共享 bearer token，不是用户级鉴权。不要把端口直接暴露到公网；
需要 TLS、访问控制或多租户时，在前面加反向代理或 VPN。

如果只是可信内网图方便，可以统一用一个非秘密占位值（例如 `local-dev-key`），
让同事不用各自配密钥；但它不是安全边界，公网或不可信网络必须换成真正的随机值。

如果局域网访问不了，依次检查：

1. 服务是否真的监听 `0.0.0.0`，而不是 `127.0.0.1`；
2. 防火墙是否放行端口；
3. 客户端是否用了正确 IP，而不是 `localhost`；
4. API key 是否一致。

## 8. Codex 与 dsh 接入

三个端口都是 OpenAI 兼容端点，区别只是实例。推荐让不同客户端或不同长会话
固定使用不同端口：

```text
Codex  -> http://<SERVER_IP>:8003/v1
dsh     -> http://<SERVER_IP>:8004/v1
批处理  -> http://<SERVER_IP>:8005/v1
```

也可以让两个客户端连同一个端口，但要接受它们共享 6 个并发槽和同一份前缀缓存。

通用字段：

```text
base_url = http://<SERVER_IP>:8003/v1
api_key  = <NINFER_API_KEY>
model    = qwen3.8-27b
stream   = true
```

Codex 的 provider 配置字段随版本变化，核心是把 OpenAI provider 的 `base_url`
指向上面的地址，并把 `env_key` 指向保存 API key 的环境变量。dsh 同理；若它使用
`OPENAI_BASE_URL` / `OPENAI_API_KEY` / `OPENAI_MODEL`，直接设置即可。

长会话必须固定端口：`8003` 的缓存不会出现在 `8004` 或 `8005`。如果网关会在多个
实例之间轮询，应按会话或 `prompt_cache_key` 做粘滞，否则每次都会冷 prefill。

## 9. 并发与容量

本机推荐 6 路。实测聚合吞吐与首 token 延迟的折中：

| 并发 | 聚合 decode | 中位 TTFT | 适用 |
|---:|---:|---:|---|
| 1 | 约 165 tok/s | 最低 | 单会话交互 |
| 4 | 约 297 tok/s | 约 5.2 s | 2–4 个活跃客户端 |
| 6 | 约 398 tok/s | 约 7.3 s | 推荐生产默认 |
| 8 | 约 496 tok/s | 约 10.0 s | 短请求突发；长上下文会更慢 |

并发越高，单请求体感越慢。6 路不是硬性要求；如果主要是一个人用 Codex/dsh，
4 路通常更跟手。`--max-pending-requests 16` 是排队上限，
`--pending-timeout-ms 600000` 是排队超时；长任务不要把这两个值调得太小。

KV 池 1,048,576 token 足够覆盖 262K 上下文和多个并发会话；`--host-kv-mib 16384`
是主机侧 KV 预留。48 GB 显存有余量不等于可以无限加并发，实际瓶颈会转到
prefill 计算、host 内存带宽和调度。

## 10. 缓存与长上下文

- 前缀缓存是**进程内**的，不跨端口、不跨重启；
- 同一个会话应固定端口；网关不要按请求轮询；
- Responses 客户端可以用 `prompt_cache_key` 表达私有续接；省略时引擎会从对话开头
  推导一个 lineage；
- 207K 级热重读在历史测试中约 73 ms、命中 99.997%，但冷请求仍要完整 prefill；
- 修改 system prompt、工具清单、图片前的内容或端口，都会让前缀失效；
- 重启实例会清空内存缓存，这是正常行为。

## 12. 回滚

保留上一版二进制和启动参数：

```bash
cp build/apps/ninfer-serve build/apps/ninfer-serve.previous
```

回滚单个端口：

1. `systemctl --user stop ninfer-8003.service`；
2. 把 `NINFER_SERVER` 指回上一版二进制，或替换 `build/apps/ninfer-serve`；
3. `systemctl --user start ninfer-8003.service`；
4. 等待 `/health` 为 `ok`，再跑 smoke test。

回滚源码补丁：

```bash
git apply --reverse /path/to/ninfer-4090-deploy/patches/ninfer-4090-stable.patch
```

不要回滚模型 revision 来“修复”性能问题；模型 SHA 不对会直接触发 artifact magic
错误。
