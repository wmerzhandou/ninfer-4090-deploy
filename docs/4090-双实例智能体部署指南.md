# 双卡 RTX 4090 48G · Qwen3.8-27B NInfer 双实例部署与调优指南

> 目标读者：在一台与本机近似硬件的新机器上部署同一套推理服务的智能体或工程师。
>
> 目标：不重复本机经历的长周期实验，直接复现已经验证过的稳定配置；遇到差异时知道先查什么。
>
> 本机验证日期：2026-11-01（Asia/Shanghai）

---

## 0. 先看结论

本机最终部署的是 **两个独立的 NInfer 实例**，不是 vLLM，也不是多卡张量并行：

| 实例 | GPU | 端口 | 用途 | 并发 | KV 池 | 关键参数 |
|---|---:|---:|---|---:|---:|---|
| `8003` | GPU1 | 8003 | 日常低延迟 Codex 入口 | 4 | `auto`（实测约 1,048,576 token） | A16 + MTP3 + K15 m12 |
| `8005` | GPU0 | 8005 | 多会话、较高吞吐入口 | 6 | 固定 `1,048,576` token | A16 + MTP3 + K15 m12 |

两者使用**同一份二进制、同一模型工件、同一组默认参数**，只差端口、显卡、并发数和 KV 容量策略。两个实例互不共享会话、缓存或 PID 文件，也不会自动负载均衡；客户端指向哪个端口，就使用哪个实例。

最终推荐参数：

```text
--max-context 262144
--prefill-chunk 2048
--kv-dtype rk4v4-e8
--prefill-activations a16
--spec mtp
--draft-tokens 3
--lm-head-draft
--prompt-lookup-tokens 15
--prompt-lookup-min-match 12
--max-pending-requests 16
--pending-timeout-ms 600000
--device 0
```

其中 `8003` 使用 `--max-concurrency 4 --kv-capacity auto`；`8005` 使用 `--max-concurrency 6 --kv-capacity 1048576`。

纯净版只去掉两个 `prompt-lookup` 参数；其余不变。极速版不是“所有场景都逐字节等价”的数学证明，而是经过真实 Codex/dsh 任务验证的日常加速档。要求严格复现时使用纯净版。

## 1. 适用硬件与边界

### 1.1 已验证硬件

- 2 张 NVIDIA GeForce RTX 4090，单卡 `49,140 MiB`（48G 魔改卡），功耗上限 `450 W`。
- 本机驱动 `590.48.01`，CUDA toolkit `12.8.61`，GCC `13.4.0`。
- 本机 CMake 实际为 `3.22.1`；仓库 README 建议 `3.28+`。新环境建议使用 3.28+；若使用 3.22.x，必须以本机已验证构建为准，并检查生成器与 CUDA 规则兼容性。
- Linux 原生部署；本机生产二进制为 `/opt/ninfer/build-sergiuszm/apps/ninfer-serve`。
- 实测功耗约 `443–448 W`，活动样本温度约 `66–76 °C`。功耗上限、驱动或散热不同会直接改变吞吐，不能把本机 tok/s 当成硬件无关常数。

### 1.2 本指南不覆盖

- Windows 专属栈（DirectStorage、D3D12）。
- 多卡张量并行；本方案是两张卡各跑一个独立实例。
- 视觉/Vision、LoRA、dashboard 等功能。
- container v3 模型工件。
- 将 INT8 prefill 或 DFlash2 K7 作为默认生产路径。
- 在没有重新做数值验收的情况下，把 K15 lookup 宣称为所有任务逐字节等价。
- DSpark；ninfer 引擎不支持，不要尝试移植。

GPU2/3 上的其它服务不属于这套双实例部署。若机器上还有别的推理任务，不要把它们的读数与 8003/8005 混在一起，也不要为了部署本指南停止无关服务。

## 3. 从零构建

### 3.1 系统依赖

Ubuntu 24.04 示例：

```bash
sudo apt-get update
sudo apt-get install --yes \
  build-essential gcc-13 g++-13 cmake ninja-build pkg-config \
  libavcodec-dev libavformat-dev libavutil-dev libswscale-dev \
  libcurl4-openssl-dev
```

确保 NVIDIA 驱动、CUDA toolkit 和 `nvidia-smi` 正常：

```bash
nvidia-smi
nvcc --version
```

### 3.2 原生构建

```bash
export CC=/usr/bin/gcc-13
export CXX=/usr/bin/g++-13
export CUDACXX=/usr/local/cuda/bin/nvcc
export CUDAHOSTCXX=/usr/bin/g++-13

cmake -S . -B build-sergiuszm -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_C_COMPILER="$CC" \
  -DCMAKE_CXX_COMPILER="$CXX" \
  -DCMAKE_CUDA_COMPILER="$CUDACXX" \
  -DCMAKE_CUDA_HOST_COMPILER="$CUDAHOSTCXX" \
  -DCMAKE_CUDA_ARCHITECTURES=89 \
  -DNINFER_BUILD_APPS=ON \
  -DBUILD_TESTING=OFF \
  -DNINFER_BUILD_BENCHMARKS=ON

cmake --build build-sergiuszm --parallel 2
```

产物：

```text
build-sergiuszm/apps/ninfer-serve
build-sergiuszm/bench/ninfer_bench
```

生产只需要 `ninfer-serve`；保留 `ninfer_bench` 便于复验 prefill/decode。构建时间取决于 CPU 和并行度，本机没有把构建时长纳入性能口径。

### 3.3 Docker 备选

仓库 Dockerfile 也可用，但本机已验证的原生路径是 CUDA 12.8.61 + GCC 13.4.0。Docker 构建通常会使用镜像内的 CUDA 版本；如果和生产二进制不同，重新测量一次锚点，不要把不同镜像的读数直接混排。

## 4. 启动脚本与运行布局

### 4.1 脚本清单

```text
scripts/start-ninfer-8003.sh        公共启动器（参数解析、健康检查、PID/日志管理）
scripts/start-ninfer-8003-fast.sh   8003 极速版：GPU1、4 路、KV auto
scripts/start-ninfer-8003-pure.sh   8003 纯净版：GPU1、4 路、无 K15 lookup
scripts/start-ninfer-8005-fast.sh   8005 极速版：GPU0、6 路、KV 1,048,576
scripts/start-ninfer-8005-pure.sh   8005 纯净版：GPU0、6 路、无 K15 lookup
```

`start-ninfer-8005-*.sh` 通过环境变量把端口、显卡、并发和 KV 容量传给同一个公共脚本；不是第二套代码。

### 4.2 环境变量

| 变量 | 默认值/说明 |
|---|---|
| `NINFER_SERVER` | 服务二进制路径 |
| `NINFER_MODEL` | 模型工件路径 |
| `NINFER_PORT` | 8003 或 8005 |
| `NINFER_VISIBLE_DEVICES` | `1` 给 8003，`0` 给 8005 |
| `NINFER_MAX_CONCURRENCY` | 1..8；8003 默认 4，8005 默认 6 |
| `NINFER_KV_CAPACITY` | `auto` 或正整数 token 数；8005 默认 `1048576` |
| `NINFER_MAX_PENDING_REQUESTS` | 默认 16 |
| `NINFER_PENDING_TIMEOUT_MS` | 默认 600000（10 分钟） |
| `NINFER_API_KEY` | 默认 `change-me`；对外暴露前必须修改 |
| `NINFER_STATE_DIR` | PID、profile、日志目录；默认在仓库的 `.run/` 下 |

注意：脚本内部始终传 `--device 0`，物理卡选择由 `CUDA_VISIBLE_DEVICES` 完成。8003 的 GPU1 不是通过 `--device 1` 实现的；不要同时改两者，否则会把设备编号重复映射。

### 4.3 启动命令

```bash
cd /opt/ninfer/sergiuszm

# 日常低延迟入口：GPU1、8003、4 路
./scripts/start-ninfer-8003-fast.sh

# 多会话入口：GPU0、8005、6 路、KV 固定 1M
./scripts/start-ninfer-8005-fast.sh

# 重启当前实例
./scripts/start-ninfer-8003-fast.sh --restart
./scripts/start-ninfer-8005-fast.sh --restart

# 只打印最终命令，不启动
./scripts/start-ninfer-8003-fast.sh --print-command
./scripts/start-ninfer-8005-fast.sh --print-command
```

启动器会：

1. 检查服务二进制和模型文件存在；
2. 检查 PID 文件指向的进程确实是本端口服务；
3. 检查端口是否被未托管进程占用；
4. 用 `setsid nohup` 启动，写 PID/profile；
5. 轮询 `/health`，最多等待 180 秒；
6. 输出 base URL、API key、模型名、PID 和日志路径。

默认日志：

```text
<repo>/.run/serve-8003/serve.log
<repo>/.run/serve-8005/serve.log
```

脚本不是 systemd unit；机器重启后需要重新执行。若改用 systemd，请把 `CUDA_VISIBLE_DEVICES`、`NINFER_SERVER`、`NINFER_MODEL`、`NINFER_STATE_DIR` 显式写进 unit，并避免和手工启动的进程重复占用端口。

## 5. 服务接口与客户端

### 5.1 统一入口

```text
8003: http://127.0.0.1:8003/v1
8005: http://127.0.0.1:8005/v1
API key: change-me
model id: qwen3.8-27b
```

健康检查：

```bash
curl -fsS http://127.0.0.1:8003/health
curl -fsS http://127.0.0.1:8005/health
```

模型列表：

```bash
curl -fsS http://127.0.0.1:8003/v1/models \
  -H 'Authorization: Bearer change-me'
```

### 5.2 Codex

Codex 使用 `/v1/responses`。新版二进制已经接受 Codex 附带的：

```json
{"include":["reasoning.encrypted_content"]}
```

这不是实际的加密推理输出；服务只把它当作 Codex 兼容提示，实际返回普通推理文本。

如果误用了旧的 stage0 二进制，会出现：

```json
{
  "error": {
    "code": "include_not_supported",
    "message": "the requested additional response fields have no available response representation",
    "param": "include"
  }
}
```

处理方式：使用本指南的新二进制；或者在旧服务前加 `/opt/ninfer/tools/include_strip_proxy.py` 之类的兼容代理，仅删除这个字段。新部署不需要 8011 代理。

Codex 与 dsh 并存时，建议各自使用独立的 `CODEX_HOME` / `DSH_HOME`，不要让两个客户端共享 session id 前缀。两个客户端可以指向同一个实例的不同会话，也可以分别指向 8003/8005；本机已验证并存路径。

### 5.3 dsh

dsh 使用 `/v1/chat/completions`，支持流式输出。它和 Codex 可以同时指向同一实例；如果担心一个客户端的重任务影响另一个客户端，分别使用 8003/8005 更简单。

### 5.4 最小 Responses 验证

```bash
curl -sS http://127.0.0.1:8005/v1/responses \
  -H 'Authorization: Bearer change-me' \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.8-27b",
    "input": "只回复 OK",
    "max_output_tokens": 64,
    "store": false,
    "include": ["reasoning.encrypted_content"]
  }' -w '\nHTTP %{http_code}\n'
```

预期：HTTP 200，返回 `object: "response"`；不应再出现 `include_not_supported`。

### 5.5 最小 Chat Completions 验证

```bash
curl -sS http://127.0.0.1:8003/v1/chat/completions \
  -H 'Authorization: Bearer change-me' \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.8-27b",
    "messages": [{"role": "user", "content": "只回复 OK"}],
    "max_tokens": 32,
    "reasoning_effort": "none",
    "stream": false
  }' -w '\nHTTP %{http_code}\n'
```

## 6. 最终参数与为什么这样定

### 6.1 参数表

| 参数 | 最终值 | 原因 |
|---|---|---|
| `--max-context` | `262144` | 模型原生上下文上限 |
| `--kv-dtype` | `rk4v4-e8` | 48G 卡可开满 262K；相对 INT8 KV 实测 decode 约 -5.7%，prefill 约 -1%～-2% |
| `--prefill-chunk` | `2048` | 比 1024 在 64K/131K prefill 上约 +1.56%/+0.89%；2688 没有继续收益，且保持 ≤2688 红线。>2688 会进入 unsplit schedule，起始精度约 1e-5 相对误差，显存大也不放宽 |
| `--prefill-activations` | `a16` | INT8 prefill 虽然快 51%–78%，但违反逐字节红线，不能默认 |
| `--spec` | `mtp` | MTP3 是已验证的稳定 decode 路径 |
| `--draft-tokens` | `3` | 与 MTP3 代码/基准口径一致；接受率和吞吐已复验 |
| `--lm-head-draft` | 开 | 官方口径的优化 proposal head |
| `--prompt-lookup-tokens` | `15` | K15 在复制型编辑上有明显收益；极速版使用 |
| `--prompt-lookup-min-match` | `12` | m12 在真实 Codex 任务中稳定；m8 虽 fixture 更快，但会让普通代码生成撞 8192 上限 |
| `--max-concurrency` | 8003=4，8005=6 | 4 是交互甜点；6 是多会话折中；8 是硬上限但冷长提示 TTFT 明显变长 |
| `--kv-capacity` | 8003=`auto`，8005=`1048576` | 8005 固定 KV 防止 8 路时 auto 吃光显存；1M token 足够普通多会话 |
| `--max-pending-requests` | `16` | 允许排队，避免并发会话直接拒绝 |
| `--pending-timeout-ms` | `600000` | 207K 冷 prefill 可能超过 30 秒；10 分钟避免排队请求被误杀 |
| `--device` | `0` | 物理卡由 `CUDA_VISIBLE_DEVICES` 选择 |

脚本没有启用 `--preserve-thinking`，也没有设置 `--default-thinking-budget`；保持默认 thinking 行为。若为了省 token 或改变多轮历史重建而修改这两个设置，必须重新跑 Codex/dsh 多轮任务，不能直接沿用本文的 TTFT/decode 结论。

### 6.2 纯净版与极速版

**纯净版**：

```text
A16 + MTP3 + rk4v4-e8 + chunk 2048
```

不启用 K15 prompt lookup。需要严格复现、排查数值问题、或做基线对照时使用。

**极速版**：

```text
A16 + MTP3 + K15 prompt lookup(min-match 12) + rk4v4-e8 + chunk 2048
```

复制型编辑实测从 `169.98` 提升到 `193.86 tok/s`（+14.0%），输出 SHA 与 MTP3 相同（在该 fixture 上）。但 K15 使用更宽的 verify，不能把“这个 fixture 相同”扩大成“所有任务逐字节相同”。真实 Codex/dsh 任务已通过，日常使用推荐极速版；数值复现要求高时切纯净版。

### 6.3 为什么不是 INT8 prefill

INT8 group-64 prefill 的性能非常好。它只影响六个 dense GEMM 的 prefill 路径（q/k/v/gate 四投影、attention output、MLP up/down 等），decode、MTP 与 DFlash verify 仍走 A16；注意力 kernel 不改：

| prompt | A16 | INT8 | 提升 |
|---:|---:|---:|---:|
| 8,192 | 2,168.0 | 3,867.9 | +78.4% |
| 32,768 | 1,991.6 | 3,393.5 | +70.4% |
| 118,000 | 1,632.8 | 2,467.8 | +51.1% |

但它关闭投机、贪心生成时，A16 与 INT8 从正文第 **242 字节** 开始分叉；两者各自可复现，但不等价。由于当前红线是“关闭投机时逐字节一致”，所以 **G2 不通过，INT8 不默认**。

INT8 的 Codex 5 任务功能上 5/5 通过，但平均墙钟 `37.3 s` 对 A16 `33.4 s`，工具调用 `34` 对 `27`，不是纯加速；INT8 + K15 还在 dsh 长清单上出现 16,384 token 上限、仅 23/30 完成。不要因为它 prefill 数字最高就默认启用。

### 6.4 为什么不是 DFlash2 K7

本机 E8 对照：

| KV | backend | K | prefill | decode | 接受率 | 相对 MTP3 |
|---|---|---:|---:|---:|---:|---:|
| `rk4v4-e8` | MTP3 | 3 | 1,991.04 | 118.69 | 56.17% | 基准 |
| `rk4v4-e8` | DFlash2 | 3 | 1,978.28 | 107.21 | 47.66% | -9.67% |
| `rk4v4-e8` | DFlash2 | 7 | 1,977.74 | 134.36 | 42.41% | **+13.20%** |
| `bf16` | MTP3 | 3 | 1,975.66 | 124.97 | 60.81% | 基准 |
| `bf16` | DFlash2 | 3 | 1,962.56 | 104.82 | 45.71% | -16.12% |
| `bf16` | DFlash2 | 7 | 1,961.78 | 97.23 | 26.81% | -22.20% |

E8 K7 的 134.36 tok/s 与 3090 参考的 140 tok/s 同量级，速度趋势成立；但 E8 K7 在代码题上与 MTP3 输出不同，bf16 K7 又在官方语料上把接受率压到 26.81%，净速度反而下降。结论：**DFlash2 K7 不是当前通用默认**，只保留为实验项。也不要把它和 K15 当成已经验证过的组合。

DFlash2 的 draft 权重是独立工件：revision `dc370fb6295a`，约 19.03 GiB；它不属于最终部署，下载和验证成本都高。若要重做 DFlash2 实验，先看 `docs/4090对照.md` 的完整记录，不要把它和主工件混淆。

### 6.5 为什么保留因果分块遍历

因果分块遍历已经在分支祖先 `694e01f0` 中，不是本次自研。隔离 A/B：

- kernel 32K/64K/128K/224K 提升 `+4.92%/+3.33%/+3.77%/+4.32%`；
- E8 端到端 64K/131K/259K 仅 `+0.61%/+1.00%/+1.47%`；
- 完整 token-id 日志逐字节一致，`cmp` 通过。

它没有达到“64K–256K prefill 提升 ≥10%”的目标，但它是 bit-exact、正收益、已在生产路径中，所以保留，不再重复开发。

### 6.6 为什么保留 q5 8-warp 与 chunk 2048

q5 LinearAdd C128 tile 从每 CTA 4 warp 改为 8 warp，计算完全相同的输出 tile，寄存器从 152 降到 84，无 spill：

| K | T | 原 4-warp | 新 8-warp | 提升 |
|---:|---:|---:|---:|---:|
| 6,144 | 512 | 399.360 µs | 368.640 µs | +8.3% |
| 6,144 | 1,024 | 605.184 µs | 568.320 µs | +6.5% |
| 17,408 | 512 | 1,068.032 µs | 995.328 µs | +7.3% |
| 17,408 | 1,024 | 1,632.256 µs | 1,549.312 µs | +5.4% |

端到端 64K/131K 为 `+0.69%/+0.36%`。chunk 2048 相对 1024 为 `+1.56%/+0.89%`；2688 没有继续收益。两者合并后：

```text
64K:  1,858.83 tok/s
131K: 1,605.58 tok/s
259K: 1,268.79 tok/s
```

关闭投机、贪心 1024-token 的 ID 轨迹 SHA-256：

```text
803edb6722348e002a2e7b3496a6702517a5ce43510ba23f841caefd0fbb1e20
```

与原版 chunk 1024/2048 相同，`cmp` 返回 0。

## 7. 并发能力：实测、甜点与上限

### 7.1 引擎硬上限

源码 `kMaximumConcurrency = 8`，`--max-concurrency` 合法范围是 1..8。超过 8 不能通过继续调参解决；需要改引擎调度/架构，属于高风险工作。

### 7.2 实测曲线

测试条件：8005，约 4K 独立提示，1024 token 输出，thinking off，单波同时发起。TTFT 包含排队和 prefill。

| 活跃请求 | 客户端聚合 decode | 含 prefill 墙钟 | TTFT 中位数 | TTFT 最慢 | 单请求 decode |
|---:|---:|---:|---:|---:|---:|
| 1 | 165 tok/s | 124 tok/s | 2.0 s | 2.0 s | 165 tok/s |
| 2 | 256 tok/s | 167 tok/s | 3.1 s | 4.2 s | 115 tok/s |
| 4 | 297 tok/s | 183 tok/s | 5.2 s | 8.6 s | 61 tok/s |
| 6 | 398 tok/s | 216 tok/s | 7.3 s | 13.0 s | 50 tok/s |
| 8 | 496 tok/s | 236 tok/s | 10.0 s | 18.3 s | 42 tok/s |

结论：

- **2–4 路**：日常交互最舒服。
- **6 路**：适合多会话，总吞吐约比 4 路高 34%，但等待变长；本机 8005 采用。
- **8 路**：总吞吐最高，约 1 路的 3 倍，但 8 个冷长提示同时到达时，最后几个请求 TTFT 可到 18 秒；只适合批量或多会话吞吐。
- **prefill 不会随并发并行加速**：decode 可以批处理，但读取长提示基本串行，这是 TTFT 变长的主因。

### 7.3 显存与 KV 容量

| 配置 | 实测显存 | 空闲 | 说明 |
|---|---:|---:|---|
| 8003，4 路，KV auto | 37.7 GiB | 10.8 GiB | 当前低延迟入口 |
| 8005，6 路，KV 1,048,576 | 38.4 GiB | 10.1 GiB | 当前多会话入口 |
| 8 路，KV 1,048,576 | 39.1 GiB | 9.4 GiB | 可用，但 TTFT 变长 |
| 8 路，KV auto | 46.9 GiB | 1.6 GiB | 不推荐；auto 把 KV 扩到 1,490,176 token |

每个实例的 KV 池是共享的，不是每路各一份：

- 1,048,576 token 池最多约 **4 个 262,144-token 满长上下文**；
- 或约 **8 个 131,072-token 上下文**；
- 普通几 K 到几万 token 的 Codex 会话，8 路容量没有问题。

“8 路并发”不等于“8 个 262K 文档同时装下”。长上下文场景先算 KV 总量，再决定并发。

### 7.4 两个实例的总能力

在两张卡独立、负载均衡的前提下：

- 8003 4 路 + 8005 6 路 = **10 路同时活跃**，聚合 decode 约 `297 + 398 ≈ 695 tok/s`；
- 两个都 8 路 = **16 路同时活跃**，聚合约 `496 + 496 ≈ 992 tok/s`，但每实例的交互延迟明显变差；
- 两个都 4 路 = **8 路同时活跃**，聚合约 `297 + 297 ≈ 594 tok/s`，体感更稳。

这是两个独立进程的吞吐相加，不是跨卡批处理；不要在客户端期待自动负载均衡。

### 7.5 临时切到 8 路

```bash
cd /opt/ninfer/sergiuszm
NINFER_MAX_CONCURRENCY=8 NINFER_KV_CAPACITY=1048576 \
  ./scripts/start-ninfer-8005-fast.sh --restart
```

只建议在批量任务或明确需要高总吞吐时这样做；日常 Codex 不建议长期 8 路。

## 9. 完整实验回顾与决策依据

这一节是给下一个智能体的“为什么”，避免把已经否决的方案重新试一遍。

### 9.1 阶段 -1：基线锚点

本机复现结果：

| GPU | 项目 | 实测 | 官方锚点 | 偏差 |
|---:|---|---:|---:|---:|
| GPU0 | sergiuszm 32K prefill | 2,032.5 tok/s | 2,027 | +0.27% |
| GPU0 | sergiuszm code decode | 147.53 tok/s | 148.6 | -0.72% |
| GPU1 | tensorninja 9.4K prefill | 3,619.3 tok/s | 3,600 | +0.54% |
| GPU1 | tensorninja 37.8K prefill | 3,288.8 tok/s | 3,250 | +1.19% |
| GPU1 | tensorninja 118K prefill | 2,465.7 tok/s | 2,578 | -4.36% |

结论：环境可信，sergiuszm 的 4090 锚点和 tensorninja 的 prefill 锚点都在 ±15% 内。

### 9.2 阶段 0：本机基线

- 32K prefill：1,983.9 ± 4.3 tok/s，落在 G0 的 1,900–2,100。
- 1024-token decode：119.30 tok/s，接受率 56.17%，G0 通过。
- 128-token decode：93.16 tok/s；512-token：98.75 tok/s。短跑低不是模型退化，而是接受率随生成段变化；因此用户确认以 **1024 token** 为稳态主口径。

### 9.3 阶段 1：DFlash2、ngram/K15

DFlash2 数据见第 6.4 节。关键结论：

- E8 K7 速度快 13.2%，但 token 序列会变；
- bf16 K7 虽然某些题与 MTP3 一致，但官方语料接受率只有 26.81%，反而慢；
- 3090 的 DFlash2 K7 约 140 tok/s，4090 的 E8 K7 约 134 tok/s，趋势同量级；
- 不作为默认。

prompt lookup：

- 旧 K3 路线在官方 32K 语料上约 +1.31%～+2.79%；
- 新 K15 独立窗口在 32K/118K 上约 +15.8%/+15.6%（m4）；
- K15 m8 在 32K 约 +10.69%，但真实 Codex task5 生成 8192 token 触顶，4/5，故否决；
- K15 m12 在复制编辑 fixture 上 `193.86` 对 `169.98 tok/s`，+14.0%，输出 SHA 相同；
- 最终选择 m12，不选择 fixture 最高的 m8。

K15 的逐字节状态：

- 同宽 K3 lookup 与 MTP3 输出逐字节一致；
- K15 使用更宽 verify，贪心 token 流与 MTP3 不保证逐字节一致；
- 现有 MTP3 在同题 1024-token 上也与 no-spec 在第 17 个 token 起分歧，因此不能把 K15 的差异单独归因于 replay 修复；
- 真实 Codex/dsh 任务通过，但严格复现请用纯净版。

### 9.4 阶段 2：INT8 prefill 失败

性能很强，但数值失败，详见 6.3。另一个重要反例：INT8 + K15 虽然复制编辑略快，但 dsh 长输出失败，只完成 23/30，不能进入极速版。

### 9.5 阶段 3：因果分块遍历

实现已在 `694e01f0`，无需重新写。隔离 A/B：

- kernel 提升 `3.3%–4.9%`；
- E8 端到端 `0.61%–1.47%`；
- 完整 token-id 日志逐字节一致。

为什么 end-to-end 只有 1%：64K prefill 的 kernel 占比中，q4 LinearSwiGLU 约 39.1%、q5 LinearAdd 约 25.0%、causal attention 约 15.9%、grouped MMA 约 13.1% + 3.8%。注意力即使再快 13%，端到端理论也只有约 15.9% × 13% ≈ 2.1%。要继续拿 10%，必须动 quantized GEMM，而不是继续在 attention 上打转。

### 9.6 最终调度收尾

- q5 8-warp：保留，端到端 +0.36%～+0.69%；
- chunk 2048：保留，+0.89%～+1.56%；
- q4 现有 WN32/C128 已是最快；grouped MMA 改 WN32 反而慢 9%–18%；q5 PingPong 无可测差异；
- 组合后 64K/131K/259K 为 `1,858.83/1,605.58/1,268.79 tok/s`；
- 贪心 1024-token ID SHA `803edb…fbb1e20` 与原版逐字节一致。

### 9.7 阶段 5：真实客户端

最终 `final-v3`：

| 客户端 | 完成率 | 平均墙钟 | 工具调用 | 平均 decode | 异常 |
|---|---:|---:|---:|---:|---|
| Codex | 5/5 | 45.59 s | 35 | 126.42 tok/s | 0 超时、0 输出触顶 |
| dsh | 5/5 | 55.45 s | 55 | 120.36 tok/s | 0 超时、0 客户端错误 |

- Codex 首次 TTFT：`4.3 / 2.4 / 2.5 / 2.4 / 2.4 s`，平均 2.80 s；后续工具回合命中私有前缀后 `0.16–1.3 s`。
- dsh 30 项长清单实际 14,136 token，30/30 完整，无 16,384 上限触发。
- dsh 早前的平均 TTFT 被缓存冷暖污染：当前 run 的 task1/task2 为 0 命中，基线 run 的 task2–5 已命中 5,832 token；不能把该平均值当 kernel 结论。

任务类型覆盖：Codex 为 bug 修复、跨文件重构、日志分析、多文件诊断、代码生成；dsh 为同类 5 项加 30 项长清单。为保护客户端内容和运行环境，原始 prompt、输出与逐事件日志不进入公开仓库；汇总指标与判定保留在本指南。

### 9.8 与 3090 的关系

本机没有 3090，3090 数据只引用工作站历史记录，不伪造：

| 项目 | 3090 历史 | 4090 本机 |
|---|---:|---:|
| 短回复 decode | 150–320 tok/s | 约 147–166 tok/s（负载相关） |
| 长上下文 decode | 65–90 tok/s | 207K 约 79.5 tok/s |
| DFlash2 K7 | 约 140 tok/s | E8 K7 约 134 tok/s |
| 207K 重读 | 约 1.3 s @99.99% | 70–80 ms @99.997% |

结论要诚实：4090 的 207K 热读明显更快，但 207K 稳态 decode 只是落在 3090 区间上半段，不能说“全面超出”。短回复也没有稳定超过 3090 的 150–320 上沿。

## 10. 故障速查

| 症状 | 先查 |
|---|---|
| 启动报 `artifact magic is not NInfer v2` | 模型 revision 下错；必须 `3526913004b1`，不能 main/v3 |
| Codex 400 `include_not_supported` | 用了旧二进制；换新二进制或加 8011 兼容代理 |
| 两个实例读数对不上 | 驱动/功耗上限是否一致；`CUDA_VISIBLE_DEVICES` 是否指错卡 |
| 8 路启动后只剩 1.6G 显存 | 用了 KV `auto`；改 `NINFER_KV_CAPACITY=1048576` |
| 6/8 路排队超时 | 提高 `--pending-timeout-ms`；本机默认已设 600000 |
| 8 路时最后几个请求等很久 | 正常：prefill 串行；不是 decode 坏了 |
| decode 变慢 | 是否误改 A16/INT8、KV dtype、chunk 或共享 kernel |
| 长上下文 262K 放不下多个并发 | KV 池共享；4 个 262K 或 8 个 128K，不是 8 个 262K |
| K15 输出与 MTP3 不完全一致 | 预期；严格复现用纯净版 |
| K15 m8 触顶 8192 | m8 太激进；用 m12 |
| DFlash2 K7 token 序列变化 | 预期；不是默认 |
| INT8 prefill 正文分叉 | 预期；数值红线不过，不能默认 |
| Codex/dsh 串台 | 共享了 session id 前缀；使用独立 `CODEX_HOME`/`DSH_HOME` |
| 服务重启后参数回到默认 | 8005 包装脚本默认 6 路/1M；8003 默认 4 路/auto；检查环境变量是否覆盖 |

## 12. 下一个智能体的最短执行路径

1. 校验模型 SHA 和二进制 SHA；如果不一致，先解决工件问题。
2. clone 上游后固定到 `7f47a622`，应用 `4090-from-origin.patch`，再把本仓库的 `scripts/start-ninfer-*.sh` 放进源码仓库。
3. 用 `CMAKE_CUDA_ARCHITECTURES=89`、GCC 13、CUDA 12.8+ 构建；保留 `ninfer_bench`。
4. 设置 `NINFER_SERVER`、`NINFER_MODEL`、`NINFER_API_KEY`、`NINFER_STATE_DIR`，启动 8003 极速版。
5. 验证 `/health`、`/v1/models`、`/v1/responses` 带 `reasoning.encrypted_content`、`/v1/chat/completions`。
6. 跑 32K prefill 和 1024-token code decode；偏差超过 10%–15% 先查环境。
7. 启动 8005 极速版（默认 6 路、KV 1M），确认两实例独立。
8. 跑 Codex 5 任务、dsh 5 任务；原始日志只保存在本地，公开前先脱敏。
9. 如需更高吞吐，再把 8005 临时切 8 路；不要默认把两个实例都拉到 8。
10. 不要提交、推送、reset 或覆盖旧二进制，除非用户明确要求；旧 stage0 二进制保留用于历史对照和回滚。

这套参数的目标不是“每个微基准都最高”，而是：**Codex/dsh 真实任务稳定、输出可控、双实例可并行、长上下文可用、显存有余量、数值问题可解释**。任何新优化如果破坏这些条件，都不应替换本指南的默认配置。
