# 实测数据与口径

本文记录验证机的参考读数，目的是让新机器有一个对照锚点，而不是把某台机器的
数字当成硬件无关常数。

## 1. 验证环境

| 项目 | 值 |
|---|---|
| GPU | 4 × NVIDIA GeForce RTX 4090 48 GB |
| 单卡显存 | 49,140 MiB |
| 功耗上限 | 450 W |
| 驱动 | 590.48.01 |
| CUDA | 12.8.61 |
| GCC / G++ | 13.4.0 |
| CMake | 4.4.5 |
| 模型 | Qwen3.8-27B NInfer，container v2 |
| 模型 SHA-256 | `eec39564993d6e9c7d5e383382a760f093465c9d163ec9a1bd6b80199514bf3e` |
| KV | `rk4v4-e8` |
| Prefill chunk | 2048 |

## 2. Prefill

| 场景 | 读数 |
|---|---:|
| 32K prompt，cold prefill，E8 KV | 约 2,030 tok/s |
| 官方 sergiuszm 32K 锚点 | 2,027 tok/s |

32K 点与官方锚点基本重合。不同驱动、功耗上限或散热会导致 ±10% 以上波动；
新机器先跑自己的基线，再判断是否需要调整。

## 3. Decode 与并发

同一实例、同一模型、`fast` 档的聚合读数：

| 活跃请求 | 聚合 decode | 中位 TTFT |
|---:|---:|---:|
| 1 | 约 165 tok/s | 最低 |
| 4 | 约 297 tok/s | 约 5.2 s |
| 6 | 约 398–399 tok/s | 约 7.3 s |
| 8 | 约 496 tok/s | 约 10.0 s |

这些是聚合 tok/s，不是单请求 tok/s。并发越高，单请求越慢；如果客户端是单人
交互，4 路往往比 8 路更跟手。

## 4. K15 与复制型编辑

同一组复制型编辑 fixture：

| 配置 | decode |
|---|---:|
| MTP3 | 170.0 tok/s |
| MTP3 + K15 lookup | 193.9 tok/s |

相对提升约 14%。K15 对“复制已有文本、局部改写、长前缀复用”更有效；对完全新的
推理内容不一定有收益。`pure` 档关闭 lookup，用于逐字节回归。

## 5. 长上下文缓存

历史测试中，207K token 级热重读约 73 ms，缓存命中 99.997%。这类读数依赖：

- 同一实例、同一端口；
- 前缀未被修改；
- 实例没有重启；
- 网关没有把请求轮询到别的端口。

冷请求仍要完整 prefill；200K 冷 prefill 不可能“秒回”。如果 64K 级请求完全
不命中，先查端口粘滞和前缀是否变化，不要先怀疑模型。

## 6. 真实客户端任务

历史验收：

| 客户端 | 任务数 | 结果 | 平均 decode |
|---|---:|---|---:|
| Codex | 5 | 5/5 通过 | 126.42 tok/s |
| dsh | 5 | 5/5 通过 | 120.36 tok/s |

任务覆盖 bug 修复、跨文件重构、长日志分析、多轮工具调用、结构化输出。当前版本
又加入了 JSON Schema 和视觉路径，部署后仍应重新跑自己的真实任务集，不要只依赖
这组历史数字。

## 7. 口径纪律

- README 的纯计算 prefill 与服务端 TTFT 不能混排；
- 对照必须同模型 SHA、同 KV dtype、同 `prefill-chunk`、同采样参数；
- 不同驱动/功耗上限的机器不能直接比较；
- 并发聚合吞吐必须注明并发数；
- 缓存命中必须注明是否同端口、是否重启、前缀是否变化；
- 任何“更快”的改动都要先过 `pure` 的逐字节回归，再看 `fast` 的体感。
