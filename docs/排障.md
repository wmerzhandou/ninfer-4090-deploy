# 排障手册

## 启动类

### `artifact magic is not NInfer v2`

模型 revision 错了。必须是 container v2 的 `3526913004b1`，SHA-256
`eec39564993d6e9c7d5e383382a760f093465c9d163ec9a1bd6b80199514bf3e`。
Hugging Face 的 `main` 已经是 v3，不要使用。

### `address already in use`

先确认是谁在监听：

```bash
ss -ltnp | grep ':8003'
```

如果是本仓库手工启动的实例：

```bash
scripts/stop-ninfer.sh --port 8003
```

如果是 systemd：

```bash
systemctl --user stop ninfer-8003.service
```

不要直接 `kill -9` 一个正在 prefill 的实例，除非你已经接受缓存清空和请求中断。

### 服务启动后很快退出

看日志：

```bash
tail -n 80 .run/8003/serve.log
# systemd:
journalctl --user -u ninfer-8003.service -n 80 --no-pager
```

常见原因：

- 模型路径不对；
- CUDA 版本不满足 12.8；
- 物理 GPU 被别的进程占满；
- `NINFER_API_KEY` 或端口被空值覆盖；
- `--host-kv-mib` 超过主机可用内存。

### 退出 SSH 后服务消失

systemd 用户服务需要 linger：

```bash
loginctl enable-linger "$USER"
```

## 请求类

### `invalid_media` / `failed to open media`

这通常是客户端发来的图片/视频数据有问题，不是模型“不会看图”。检查：

- base64 是否完整；
- MIME type 和文件头是否匹配；
- 图片是否能被 `ffprobe`/浏览器正常打开；
- 请求体是否被网关截断。

可以先用 `scripts/smoke-test.sh --image test.jpg` 验证服务端视觉链路。

### `499` 或 `client disconnected`

通常是上游客户端主动取消（超时、用户停止、网关断开），不是引擎把服务打挂。
看请求日志里的状态码和上游取消时间；如果大量出现，检查客户端超时和网关超时。

### `HTTP 500` 后整机 `503`

旧版引擎会把单个请求异常升级为永久 `failed_` 锁存。本版本已改为：

- 打印真实 `what()`；
- 清理该请求后原地恢复；
- 5 分钟内连续 3 次致命异常才退出交给 systemd。

如果仍然出现，先查：

```bash
grep -a 'FATAL engine worker failure' .run/8003/serve.log
grep -a 'failed during generation' .run/8003/serve.log
```

并确认 systemd 的 `Restart=on-failure` 和 watchdog 正常。

### `unsupported_json_schema`

当前 JSON 约束路径不支持 DFlash 后端。生产默认是 MTP3，不要切到 DFlash 后还
期待 JSON Schema。使用 `fast` 或 `pure` profile（都带 `--spec mtp`）。

### `constraint_dead_end`

Schema 本身可满足，但在当前 `max_tokens` 内无路可走。处理：

- 提高请求的 `max_tokens`；
- 去掉不必要的 `minLength` / 复杂组合；
- 简化嵌套对象；
- 避免要求模型在极短输出里完成大量字段。

### JSON 输出被截断

`finish_reason=length` 表示 `max_tokens` 用完，不是引擎忽略了 schema。提高
`max_tokens` 或缩短要求。注意思考 token 也占输出预算。

### 工具调用与 JSON 同时使用被拒

当前约束契约不允许“可调用工具 + JSON 输出”同时出现，因为无法保证两个输出通道
都合法。拆成两次请求：先决定工具调用，再生成 JSON；或去掉工具。

## 缓存类

### 64K/200K 请求完全不命中

按顺序查：

1. 请求是否被网关轮询到另一个端口；
2. 是否重启过实例；
3. system prompt、工具清单、图片前内容是否变化；
4. 是否使用了不同的 `prompt_cache_key`；
5. 是否把 `mode:"explicit"` 配错，导致共享前缀没有写入。

缓存是进程内的，不跨端口、不跨实例、不跨重启。长会话应固定端口。

### 首 token 很慢，但后续很快

这是正常的 cold prefill。200K 冷请求需要完整读入；只有同前缀的热请求才会走缓存。

## 性能类

### 比参考读数慢很多

依次检查：

- `nvidia-smi` 的功耗上限是否 450 W；
- 驱动和 CUDA 是否与参考环境一致；
- 是否误用了 container v3 或不同模型 SHA；
- 是否把 `--prefill-chunk` 改得太大；
- 是否把 `--max-concurrency` 拉到 8 以上；
- 是否有其他进程占用 GPU/CPU；
- 是否在 `pure` 档测，却拿 `fast` 的读数对比。

### decode 变慢

可能误伤了 decode 共享 kernel，或把 JSON 约束、视觉、K15 混在了不该混的档位。
先用 `pure` 复测，再逐项启用 `fast` 的 lookup；不要一次改多个变量。

### 视觉请求变慢或 OOM

- 降低 `--vision-max-tokens`；
- 降低并发；
- 缩小图片分辨率；
- 避免一次请求塞入多张大图；
- 确认不是 `invalid_media` 导致的重试。

## 运维类

### 服务健康但客户端连不上

```bash
curl -v http://127.0.0.1:8003/health
curl -v http://<SERVER_IP>:8003/health
```

本机通、局域网不通，通常是绑定地址或防火墙问题。默认应绑定 `0.0.0.0`。

### systemd 反复重启

```bash
systemctl --user status ninfer-8003.service
journalctl --user -u ninfer-8003.service -n 120 --no-pager
```

如果 10 分钟内失败 5 次，systemd 会停止重试：

```bash
systemctl --user reset-failed ninfer-8003.service
systemctl --user start ninfer-8003.service
```

### watchdog 误重启

watchdog 默认连续 3 次 `/health` 失败才重启，且重启后 sleep 60 秒。若模型加载
本来就超过 5 分钟，调大 `NINFER_WATCH_TIMEOUT` 或 `NINFER_WATCH_INTERVAL`，不要
直接关闭 watchdog。

## 最小排查顺序

1. `curl /health`；
2. `nvidia-smi`；
3. 看 `serve.log` 的 `FATAL` / `failed during generation`；
4. 用 `scripts/smoke-test.sh` 复现；
5. 只改一个变量，再复测；
6. 需要回滚时先停单端口，不要一次停三个实例。
